Both facts show the byte-identity requirement mis-attributed legitimate normal-instance activity to T13.2. That rule is hereby repaired, not the product.

## 2. New run-domain model (supersedes the old quiescence requirement)

**Normal Harness domain** — `/Users/tongxin/.dsh`, `127.0.0.1:3080`:
- MAY keep running for the entire T13.2 lifecycle.
- MAY normally create/modify its own sessions, workspaces, storages, settings, and serve other plugin development.
- Its writes are NEVER attributable to T13.2. Stopping it, killing its process (e.g. PID 18918), or touching its state to obtain a "clean baseline" is FORBIDDEN.

**T13.2 domain** — a repository-external disposable runtime (e.g. `/Users/tongxin/Developer/Harness/.t13-2-followup-<RUN_ID>/home`) with `DSH_HOME` explicitly injected into every launched process, listening on `127.0.0.1:18795` (never connecting to 3080). It owns independent DSH_HOME, workspace, profile, sessions, storage, runtime state, logs, and temporary files, and never uses the real `~/.dsh` as a writable runtime directory.

## 3. Replacement invariant (new F3, exact wording)

> **"T13.2-originated processes MUST NOT write to the real user DSH_HOME."**
>
> The acceptance object is **attribution**, not global quiescence. Changes to the real `~/.dsh` during a T13.2 validation do NOT constitute failure by themselves. A change constitutes an isolation failure ONLY if it is proven to be produced by a T13.2 process, subprocess, runtime, or its toolchain. The normal Harness's legitimate concurrent activity must never produce a false T13.2 failure.

The superseded invariant — "the real `~/.dsh` must remain byte-identical / unchanged during validation" — and the derived rule "STOP if the normal Harness is running and may write `~/.dsh`" (`T13_2_FOLLOW_UP_BLOCKED_NORMAL_HOME_NOT_QUIESCED`) are **DEPRECATED and replaced** by this section. The corresponding clause in `DSH_IDEA_T13_2_REAL_BROWSER_PROVIDER_PROTOCOL_FREEZE.md` is amended in place (original text preserved above the amendment).

## 4. Provider configuration template contract

- Path: `/Users/tongxin/Developer/Harness/.t13-2-provider-template/` containing `settings.yaml` + `.credentials.yaml`.
- Creation — **whole-pair stable snapshot protocol** (the normal Harness may legally rewrite `~/.dsh/settings.yaml` at any moment, so independently-stable per-file copies could still come from DIFFERENT configuration windows; each attempt must therefore prove the PAIR is stable): at the start of the follow-up execution round, ONE attempt consists of, in order: (1) read `settings_before`; (2) read `credentials_before`; (3) copy `~/.dsh/settings.yaml` → temporary copy inside the rig; (4) copy `~/.dsh/.credentials.yaml` → temporary copy inside the rig; (5) read `settings_after`; (6) read `credentials_after`. The pair is accepted ONLY if `settings_before == settings_after` **AND** `credentials_before == credentials_after`. If EITHER file changed during the attempt: delete BOTH temporary copies of that attempt immediately, and retry the WHOLE pair from step (1) — a partially stable file must never be carried over or reused in the next attempt. Bounded retry budget: **3 attempts with short backoff**. If no pair-stable snapshot exists after the bounded retries: **STOP — `T13_2_BLOCKED_PROVIDER_TEMPLATE_SNAPSHOT_UNSTABLE`**; no partial template is kept.
  - Secret-safe comparison for `.credentials.yaml`: the equality check may only ever produce an **in-memory boolean result** (e.g. a `cmp -s` exit status). It is FORBIDDEN to record or emit any hash, size, byte, prefix, suffix, diff, or other comparison material of the credential file into any report, log, evidence artifact, or Git object.
  - On acceptance, and only then: BOTH files are published together to `/Users/tongxin/Developer/Harness/.t13-2-provider-template/` with destination `.credentials.yaml` mode `0600`; provenance (creation timestamp, "whole-pair verbatim snapshot of the user's officially configured provider settings at one stable instant", attempt count) is recorded in the follow-up report WITHOUT any secret material. Until this protocol runs, the template does not exist; this repair documents the contract only — no secret file is created during a docs-only phase.
- The template is repository-external, never committed to Git, never referenced by any tracked file, and never used directly as a `DSH_HOME`.
- At each T13.2 runtime boot, the allowed configuration files are copied FROM the template INTO the disposable `DSH_HOME`; from then on the runtime operates exclusively on the disposable home. The template itself stays read-only during the run (any modification attempt is an isolation failure).
- No secret value, hash, size, prefix, suffix, or Authorization material may enter reports, logs, evidence, or Git artifacts.
- Should an equivalent, safer repo-external mechanism already exist, it may be substituted with its exact path and provenance recorded.

## 5. Attribution proof design (minimal sufficient)

The follow-up round must produce the following evidence; together they satisfy A–F without ever stopping the normal Harness:

- **A — isolated env injection**: the rig launch script and each boot log record the exact command line with explicit `DSH_HOME=<runtime>/home` (and the guard `--import` preload) for every T13.2 process. No T13.2 process is ever launched without it.
- **B — port separation**: `lsof` evidence that the T13.2 Host listens on 18795 only; 3080 remains owned by the normal instance's PID; the browser session tokens/cookies of the two instances are never exchanged.
- **C — disposable state containment**: directory inventory of the runtime showing `profiles/`, `sessions/`, `storages/`, `workspace/` all inside the disposable home; the workspace created via the official Host Remote has its path inside the runtime; the profile's installed plugin lives in the runtime's profile `node_modules`.
- **D — no write target into the real home (deterministic/continuous, NOT sampled)**: write isolation of the T13.2 process tree is proven by one of the following mechanisms, chosen in this priority order and verified by a mandatory activation self-test BEFORE any scenario runs; periodic `lsof` sampling is explicitly **insufficient as primary proof** (an `open → write → close` between two samples would be invisible) and may be retained only as auxiliary evidence:

  - **A (preferred) — process-scoped filesystem write denial**: the T13.2 Host process and all descendants are launched inside a macOS seatbelt sandbox (`sandbox-exec -f <rig>/deny-dsh-write.sb node …`) whose profile contains a targeted denial of every write-class operation (`file-write*`: create/write/append/rename/unlink/truncate) against `/Users/tongxin/.dsh/**`, everything else permitted as before. A denied write fails loud (EPERM) inside the T13.2 process, is recorded in the rig log, and is an **immediate isolation-failure STOP** — it can never silently mutate the real home. The profile grants nothing to, and revokes nothing from, the normal Harness process, and the real `~/.dsh` permissions are never modified. **Activation self-test (strictly non-mutating)**: before boot, a child process inside the SAME sandbox attempts exactly `open("/Users/tongxin/.dsh/settings.yaml", O_WRONLY)` — a pre-existing, non-secret-bearing real DSH_HOME file — and NOTHING else. FORBIDDEN in the probe: `O_CREAT`, `O_TRUNC`, `write()`, append flags, `rename`, `unlink`, `chmod`, or any metadata mutation; `.credentials.yaml` must never be a probe target. **PASS** = the open is denied by Seatbelt (EPERM or equivalent). If the open unexpectedly SUCCEEDS: close the descriptor immediately, perform NO write or any other mutation, record mechanism A activation as FAILED, do not use mechanism A, and fall back to mechanism B. Destructive canaries against the real home (create-then-cleanup probes) are FORBIDDEN as self-tests. The sandbox profile and the self-test result are recorded in the report.
  - **B (fallback) — reliable continuous process-attributed mutation trace**: e.g. Endpoint Security streaming (`eslogger` with the create/write/close/rename/unlink/truncate event set) or a continuous `fs_usage`-class trace, filtering exactly `/Users/tongxin/.dsh/**`, covering the ENTIRE T13.2 runtime lifetime (from before first boot to after final shutdown), the T13.2 process AND all descendants, capturing every WRITE/CREATE/RENAME/DELETE/TRUNCATE mutation with **no observation gap between or inside scenarios**. **Activation self-test**: before boot, the trace is started and a canary mutation inside the T13.2 domain is performed and must be observed in the stream; only then may scenarios begin. Any trace event matching `~/.dsh/**` attributable to a T13.2-descendant PID is an immediate isolation-failure STOP. Trace logs stay in the rig (deleted at cleanup; safe summary in the report).

  - **Neither mechanism verifiable** (self-test fails for A and B): **STOP — `T13_2_BLOCKED_ATTRIBUTION_PROOF_UNAVAILABLE`**. The proof standard is never lowered to proceed.
  - **Prohibited rule (false-negative guard)**: attributing a real-home diff path to the normal Harness merely because no `lsof` open handle was observed on it at sampling time is FORBIDDEN. The success verdict **`REAL_DSH_HOME_WRITTEN_BY_T13_2 = FALSE`** is valid ONLY when supported by mechanism A or B above; the scoped before/after manifest diff remains mandatory corroborating evidence (any diff path must be explainable as normal-instance activity, and mechanism A/B guarantees no T13.2-originated mutation could have occurred regardless).
- **E — scoped before/after manifests as CORROBORATING evidence (attribution semantics fixed)**: full secret-safe manifests (path + size inventory; the credential file compared by boolean equality only) are captured before boot and after cleanup. The manifest diff NEVER attributes real-home paths by itself, and never by the absence of an `lsof` handle. The attribution authority is the write-isolation mechanism alone, with these exact semantics: **mechanism A** — successful enforcement (verified by the non-mutating self-test) proves that a T13.2-originated real-home mutation COULD NOT OCCUR during the protected runtime, so every real-home diff path is normal-instance activity by construction; a Seatbelt-DENIED write attempt is not a filesystem mutation and is never counted as one. **mechanism B** — a traced T13.2-descendant mutation event against `~/.dsh/**` IS direct attribution evidence and causes an immediate isolation-failure STOP. The report states the verdict as `REAL_DSH_HOME_WRITTEN_BY_T13_2 = FALSE` (success) — the previous literal byte-identity verdict is retired.
- **F — safe deletion**: cleanup deletes only the runtime directory tree. Its safety rests on: (1) disposable runtime containment (all T13.2 state — profiles, sessions, storages, workspace, logs — lives inside the runtime); (2) the isolated `DSH_HOME` injected into every T13.2 process; (3) the active write-isolation mechanism (A's deterministic denial or B's continuous attributed trace, as verified by its self-test); and (4) no dependency or reference from the real `~/.dsh` into the disposable runtime (the real home is never configured to point at, mount, or resolve the runtime). **Zero-handle `lsof` scans carry no deletion authority**; if retained at all, they are auxiliary observations only (V1 semantics retired). Deletion therefore cannot affect the normal instance or the real home.
